### A job for a workflow this application does not own needs an answer of its own (OPEN, Stephan decides)

This entry records what was measured and what the options are. The behaviour is NOT changed in this branch,
because the fix does not fit inside this adapter.

Where two applications hang on one cluster and share a job type, the cluster hands each job to whichever of them
asks first. The same shape occurs without two applications: a process instance left behind by an earlier run holds
a `canceling` listener job, and the next worker of that job type is served it.

What happens today was traced rather than guessed. The adapter reads the workflow aggregate id out of the job and
hands the delivery to the platform. The platform loads the aggregate, finds nothing, and throws with the message
`No workflow aggregate of class '%s' having the ID '%s' was found ... it must not be deleted while the workflow is
active`. Three things follow from that:

- the message accuses the developer of deleting an aggregate, and says nothing about the job belonging somewhere
  else;
- the user-task listener path fails such a job with no retries left, which is deliberate for a notification that
  failed and wrong here: the cluster raises an incident on the FIRST delivery, and the user task stands in
  `CREATING` or `CANCELING` until an operator resolves it;
- no delivery record is written, because the transaction rolled back, so every redelivery repeats it, and the
  application which owns the workflow never gets the job.

So it is not consumed quietly. It is consumed loudly, under the wrong name, and the right application still does
not get it.

The remedy asked for was "warn and hand the job back". The adapter alone cannot do it. It has no way to tell this
failure from any other: what reaches it is an `IllegalStateException`, and reading its text would tie this adapter
to a sentence in another repository. What is missing is an inbound answer meaning "this workflow is not mine". The
SPI has `WorkflowAwareness` with `UNKNOWN_TO_BPMS`, but only for the outbound election; `WorkflowTaskOutcome.Kind`
has `COMPLETED`, `COMPLETION_PENDING` and `BPMN_ERROR` and nothing else.

Three ways out, for Stephan to choose between:

1. the platform answers the delivery with a new outcome meaning "not mine", and every adapter decides what to do
   with it. In Camunda 8 that would be a WARN naming the workflow and a fail command with the retries UNCHANGED
   plus the configured backoff, so the cluster offers the job again and the owning application can take it. That
   is a flight over the platform and all adapters;
2. the platform keeps throwing but throws a type of its own, and the adapters recognise the type. Smaller, and it
   leaves the decision about retries with each adapter;
3. nothing changes in the code, and the case is documented as the price of a shared job type. The wiki paragraph
   this branch adds already says it.

One risk belongs to options 1 and 2. Where NO application owns the aggregate, which is exactly the leftover
instance, a job handed back bounces between the cluster and whoever asks, forever. Whatever is chosen needs an end
to that: a count of hand-backs, or a backoff which grows.

## Where this is referred to
