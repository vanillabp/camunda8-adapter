### Correction to decision 9: a busy cluster takes every completion and failure of a job

A correction, added by story 2098 on 2026-11-07, to the first paragraph of decision 9. That
paragraph says that a cluster under load rejects commands and that a rejected completion costs the
job a retry. For the completion and the failure of a job this is wrong. The reason stays different
for the other commands, and the rule of decision 9 itself stands.

**What a busy cluster refuses.** The broker's flow control keeps a list of commands it always
takes (`WhiteListedCommands` of `zeebe-logstreams`). A command on that list passes the request
limit (`RequestLimiter#acquire`) and the write rate limit (`FlowControl#tryAcquireInternal`). The
completion and the failure of a job are on the list on 8.8, 8.9 and 8.10. The BPMN error and the
change of a job timeout are on it on no line. The completion of a user task is on it on 8.8.46 and
8.9.28, and not on 8.10.7.

Measured on 2026-11-07 against `camunda/camunda` 8.8.46, 8.9.28 and 8.10.7, each with a request
limit of one (`ZEEBE_BROKER_FLOWCONTROL_REQUEST_ALGORITHM=fixed`, `..._FIXED_LIMIT=1`). Each burst
is 300 requests at once, each against a job or a user task which exists. The numbers are accepted
requests / requests refused with `503 RESOURCE_EXHAUSTED` (REST) or `RESOURCE_EXHAUSTED` (gRPC).
No request got any other answer.

|       Command        | Transport |  8.8.46   |  8.9.28  |  8.10.7  |
|----------------------|-----------|-----------|----------|----------|
| job completion       | REST      | 300 / 0   | 300 / 0  | 300 / 0  |
| job completion       | gRPC      | 300 / 0   | 300 / 0  | 300 / 0  |
| job failure          | REST      | 300 / 0   | 300 / 0  | 300 / 0  |
| job failure          | gRPC      | 300 / 0   | 300 / 0  | 300 / 0  |
| BPMN error           | REST      | 62 / 238  | 79 / 221 | 53 / 247 |
| BPMN error           | gRPC      | 102 / 198 | 67 / 233 | 58 / 242 |
| job timeout change   | REST      | 76 / 224  | 60 / 240 | 43 / 257 |
| job timeout change   | gRPC      | 103 / 197 | 56 / 244 | 51 / 249 |
| user task completion | REST      | 300 / 0   | 300 / 0  | 59 / 241 |

A user task has no gRPC command. The split between accepted and refused moves from run to run.
Whether a command is refused at all does not. `Camunda8WhatABusyClusterRefusesIT` holds this on
every line, and a line which changes the list turns it red.

**Where 19.433 of 20.000 came from.** Probe P5b of the spike `analysis-c8-client-recommendations`
(2026-08-18) sent 20.000 commands over gRPC with the plain client to a single node
`camunda/zeebe:8.8.31`, with the default flow control, and 19.433 came back as `RESOURCE_EXHAUSTED`.
The spike's result names only "commands". The probe's source and its write-up
(`c8-probes-RESULT.md`) were in a scratchpad which no longer exists. On 8.8.31 the completion and
the failure of a job are on the list as well, so those commands were not completions or failures of
a job. The number says that a busy cluster refuses SOME commands in large numbers. It says nothing
about the commands a job handler sends back, and decision 9, the wiki, the README and the javadoc
of `Camunda8CommandRetry` used it for exactly that.

**What still refuses a completion.** Three ways, and none of them goes through the list:

- a broker which is short of disk space refuses every command with `RESOURCE_EXHAUSTED`, before
  the flow control is asked (`CommandApiRequestHandler#handleExecuteCommandRequest`, on all three
  lines)
- on 8.10 a partition which is paused for a leadership transfer refuses every write with
  `RESOURCE_EXHAUSTED` (`FlowControl#tryAcquireInternal`, `Rejection.PartitionPaused`)
- a request which gets no answer within the request timeout, or meets a partition whose leader
  just changed (`UNAVAILABLE`, HTTP `503` without `RESOURCE_EXHAUSTED`)

**The rule now.** `Camunda8CommandRetry` stays around all four commands. For the BPMN error, the
lock renewal and (on 8.10) the completion of a user task it waits out a busy cluster. For the
completion and the failure of a job it waits out the three cases above: an answer which did not
come, a short disk and a leadership transfer. The reason in decision 9 changes, the code does not.

Open for Stephan: whether the retry stays for the completion and the failure of a job, where flow
control is not the reason any more. Default: it stays, because a timeout without an answer and the
leadership transfer on 8.10 still cost the job a retry without it.
