### A test on Camunda Process Test gets its cluster per test method, through an artifact of its own

Built on 2026-11-24.

Camunda Process Test is Camunda's own way to test a process application. Its Spring integration,
`@CamundaSpringProcessTest`, does three things which an adapter that builds its own client at
startup cannot live with:

- Its execution listener asks for the application context before it starts its cluster. So
  there is no cluster while the context starts, and the adapter waited for one until
  `startup-wait` ran out.
- It creates a client before each test method and publishes it in a
  `CamundaClientCreatedSpringEvent`. Before the client goes, after the method, it publishes a
  `CamundaClientClosingSpringEvent`.
- After each test method it deletes everything its cluster holds, the deployments included, and
  the cluster then counts its keys from the start again.

What holds now:

- The artifact `camunda8-adapter-spring-boot-process-test` carries the support. An application
  adds it as a test dependency next to Camunda's own one. Its auto-configuration is active only
  where the context holds the marker bean `CamundaSpringProcessTestContext`, which
  `@CamundaSpringProcessTest` imports. A test class of the same application without the
  annotation stays on the configured cluster.
- The production artifacts do not change their behaviour. `camunda8-adapter-spring-boot` only
  learns to read a bean of type `Camunda8ClusterOfATestRuntime`. Without it, which is every case
  outside such a test, the client is built at startup as before. Camunda Process Test and with it
  Camunda's Spring starter are `provided` in the new artifact, so they reach no production
  classpath. The adapter keeps using the plain Java client.
- In that mode the client factory builds no client at startup. The platform deploys every workflow
  module and starts its processing once, at a moment when there is no cluster. The deployment
  service keeps both and does them again with every cluster that arrives: wait for the cluster,
  deploy, open the workers. Before the cluster leaves it closes the workers the way a shutdown
  closes them, and then the factory closes its client.
- The adapter builds its own client against the address and with the credentials of the client of
  Camunda Process Test. It does not use that client. So the execution model, the worker defaults
  and the timeouts of the adapter's configuration hold in a test as they hold in production.
- The delivery id of a job is the job key followed by a mark of the handover. The delivery log of
  the application keeps its records across test methods, while each cluster hands out the same
  keys again. With the plain job key the third test method of a class met a record of the first
  one, and the core refused the delivery. Outside such a test the delivery id stays the job key.
- The configured connection keys are not used in that mode. The start says so in one line and
  names the keys the application wrote. Every check which does not depend on the connection runs
  as before.
- The client for the test runtime reads no environment variables of the Camunda client. A
  `CAMUNDA_REST_ADDRESS` or `ZEEBE_GRPC_ADDRESS` would otherwise win over the address of the test
  runtime, and the test would run against another cluster without a word.
- A test method waits one minute for the cluster of the test runtime, unless the application set
  `startup-wait`. The default of ten minutes is for a cluster which boots with the application.
  The cluster of a test runtime is running already.
- A test class with `@CamundaSpringProcessTest` whose classpath lacks the artifact ends its start.
  `camunda8-adapter-spring-boot` finds the marker bean of Camunda Process Test by the name of its
  type, and the message names the artifact. Without it the adapter would wait for its configured
  cluster for the whole `startup-wait`.
- Each handover forgets the tenants the deployment checked against the cluster before, because
  the test runtime may have deleted them.

Why not the other ways:

- A conditional auto-configuration in `camunda8-adapter-spring-boot` itself would have spared the
  application one dependency. It has to compile against the events, which live in Camunda's Spring
  starter, so the production POM would name the starter. It would be optional, but it is a
  dependency per release line on a Spring Boot specific artifact, and the adapter promises to use
  the plain Java client only. Reading the events by reflection would avoid the dependency, at the
  price of code which breaks without a compiler noticing.
- Using the client of Camunda Process Test directly would have left the workers on that client's
  own executor and defaults, so a test would not run the workers the way production runs them.
- Starting the cluster before the context (the way the integration tests of this repository and
  the upgrade guide did it) works, but it asks every test of an application to change its setup,
  and Camunda Process Test then deletes the deployment after the first test method anyway.

Quarkus has no integration of Camunda Process Test, so there is nothing to follow there.

Known limits, also on the wiki page `Testing`:

- The mark of the handover is new with every test method, also where the cluster kept its data
  (`data-deletion-mode: none` on 8.10, or a remote runtime). A job which a method left to its lock
  then comes back in a later method under a new delivery id, and its handler runs a second time.
  Renewing the mark only for an emptied cluster would need a request per test method to find out
  whether the cluster was emptied, and on 8.8 that request deploys a marker process into the
  cluster of the test.
- An adapter id which production boots degraded, because its connection keys are missing and its
  `deployment-failure` is `warn`, is fully active in such a test. Its connection comes from the
  test runtime, so no key is missing there.
