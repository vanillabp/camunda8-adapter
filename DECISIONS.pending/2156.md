# A user task with a job type of its own still gets the cluster's user-task job

*Pending. It corrects a fact which decision 53 and decision 54 rely on, and it asks the maintainer
whether the rule of decision 53 should change.*

Decision 53 says that a user task without `zeebe:userTask` but with a `zeebe:taskDefinition` of its
own is served by a worker of the application, under the job type the application chose. So the
reader of job-worker user tasks passes over it, and the refusal named the job type as a third way
out.

Measured against `camunda/camunda:8.10.9` on 2026-11-13 (`Camunda8LegacyUserTaskIT`): the cluster
ignores that job type. It hands out a job of type `io.camunda.zeebe:userTask` for such an element,
exactly as for one without a `zeebe:taskDefinition`. A worker which subscribes to the job type of the
model never gets the job.

What this branch changes, without changing the rule of decision 53:

- The refusal of a job-worker user task no longer offers the `zeebe:taskDefinition` as a way out,
  because that way out does not work.
- A `@WorkflowTask` method which names the job type of such a user task ends the boot with a message
  which says that the cluster ignores the job type. Before, the core said that the method matches no
  task.

What stays as it was, and is the question: a claimed process with such an element and no method for
its job type still deploys without a word, and its workflows stand at the element. The default
proposal is to treat the element like every other job-worker user task (refuse it in a claimed
process) and to supersede the third-way-out paragraph of decision 53 with a new entry.

A version the cluster already holds may keep a job-worker user task. Where workflows still run on
such a version, the start warns in "DEPLOYED VERSIONS" and names the way out measured in the same
run: a process instance migration in Operate to a version with a Camunda user task, and for an
instance which already stands at the user task a process instance modification after it (cancel the
token, add a new one at the same element). The migration alone creates the Camunda user task without
running its `creating` listeners, so VanillaBP never hears of it.
